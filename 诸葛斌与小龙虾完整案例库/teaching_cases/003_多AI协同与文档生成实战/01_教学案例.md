## 三、教学分析

### 3.1 多 AI协同架构

```
┌─────────────────────────────────────────────────────────┐
│                    用户（钉钉）                          │
│                       ↓  ↑                               │
│              ┌──────────────┐                           │
│              │  小龙虾(OpenClaw) │ ←─── AI 处理层        │
│              │  Qwen 3.5 Plus  │                           │
│              └──────┬───────┘                           │
│                     │ NFS 共享存储                       │
│              ┌──────┴───────┐                           │
│              │  诸葛马(Hermes) │ ←─── 前端代理层          │
│              │  DashScope API  │                           │
│              └──────────────┘                           │
└─────────────────────────────────────────────────────────┘
```

**架构特点：**
- **前端代理**：诸葛马负责消息路由和前缀匹配
- **AI 后端**：小龙虾负责复杂 AI 处理和文件生成
- **通信层**：NFS 共享存储实现跨服务器通信
- **用户入口**：钉钉直连小龙虾，透明转发

### 3.2 关键技术点

| 技术 | 说明 | 教学价值 |
|------|------|----------|
| NFS 共享存储 | 阿里云 VPC 内网 NFS，延迟 < 1ms | 跨服务器通信方案 |
| 消息队列 | `/shared/messages/from-lobster/` 和 `from-hermes/` | 异步通信模式 |
| 兜底检测 | 正则匹配 `收到你的消息:.*Hermes已处理` | AI 回退机制 |
| 代理中转 | 诸葛马 → 小龙虾 → 用户 | 多 AI协同模式 |
| 文档生成 | Python (python-docx, python-pptx) | AI 文档生产能力 |
| 数据检索 | SearXNG + web_fetch + 百度百科 | AI 网络搜索能力 |

### 3.3 错误处理案例

**案例：拼写错误导致通信失败**

```
用户输入：诸葛玛，写一篇...
           ↑ 错误：玛 ≠ 马

Hermes 日志：📩 收到消息 (非诸葛马前缀，跳过)

解决方案：小龙虾直接代写
```

**教训：**
1. 前缀匹配是精确匹配，拼写错误会导致通信失败
2. AI 应具备容错能力（代写 fallback）
3. 用户输入时需注意关键标识的准确性

## 五、反思与讨论

### 5.1 成功经验

1. **多 AI协同模式可行**：NFS + 消息队列实现稳定通信
2. **AI 代理中转有效**：诸葛马作为前端代理，小龙虾作为 AI 后端
3. **文档生成质量高**：从占位符到真实数据，迭代提升
4. **用户体验流畅**：钉钉直连，无需切换平台

### 5.2 改进空间

1. **拼写容错**：诸葛马应支持模糊匹配（诸葛玛 → 诸葛马）
2. **通信延迟**：AI 生成耗时 36 秒，可优化
3. **数据准确性**：部分数据为估算值（如在校生 3.6 万）
4. **错误提示**：通信失败时应给用户明确提示

### 5.3 讨论问题

1. 多 AI协同架构中，前端代理和 AI 后端的职责如何划分？
2. NFS 共享存储 vs API 调用，哪种跨服务器通信方式更优？
3. AI 生成的文档数据如何验证准确性？
4. 拼写错误、通信超时等异常情况如何处理？
