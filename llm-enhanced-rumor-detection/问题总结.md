# 原代码问题总结

## 🔴 核心问题

### 问题 1：训练极慢（两天才 8 个 epoch）

**根本原因**：`use_mock_llm: false`，导致训练时每个样本都调用 DeepSeek API。

**具体表现**：
- 每取一个训练样本，对样本里的每条帖子都调用一次 DeepSeek API
- API 调用有 1 秒强制延迟（`request_delay = 1.0`）
- 如果一个 claim 有 50 条帖子，光生成 explanation 就至少 50 秒
- 加上网络延迟、推理时间、编码时间，一个样本可能需要 1-2 分钟
- 每个 epoch 都会重新生成 explanation（没有真正的缓存机制）

**代码位置**：
- `config/default.yaml` 第 75 行：`use_mock_llm: false`
- `src/data/dataset.py` 第 117-144 行：`_generate_explanations()` 方法
- `src/data/llm_explanation_generator.py` 第 43-54 行：`_rate_limit()` 强制延迟

**影响**：
- 原配置 200+100 epoch，按此速度需要 **75 天**
- 即使改成 10+5 epoch，也需要数天

---

### 问题 2：准确率只有 0.33（二分类）

**根本原因**：多重因素叠加。

**可能原因**：
1. **训练轮数太少**：只跑到第 8 个 epoch，模型还没充分学习
2. **LLM 生成质量不稳定**：API 失败时会返回固定模板文本，导致 explanation 没有信息量
3. **训练流程不稳定**：每个 epoch 都重新生成 explanation，训练不可复现
4. **配置过重**：100 posts、256 explanation length、batch size 1

**代码位置**：
- `src/training/trainer.py` 第 264-274 行：计算的是 `rumor_accuracy`（二分类）
- `src/training/trainer.py` 第 307-309 行：训练日志打印的是 `rumor_acc`

**说明**：
- 训练日志里的 `accuracy` 指的是**谣言二分类准确率**
- 不是四分类立场准确率
- 0.33 对二分类来说明显偏低，说明模型效果不好

---

### 问题 3：配置过重

**原配置**：
```yaml
num_epochs_phase1: 200
num_epochs_phase2: 100
max_posts_per_claim: 100
max_post_length: 128
max_explanation_length: 256
```

**问题**：
- 总共 300 个 epoch，训练时间过长
- 每个 claim 最多 100 条帖子，数据量大
- 序列长度过长，显存占用大

**影响**：
- 训练时间长
- 显存占用大，容易 OOM
- 不适合快速验证

---

### 问题 4：冗余日志拖慢训练

**代码位置**：`src/training/trainer.py` 第 265-272 行

**原代码**：
```python
print(f"\nDEBUG - Rumor Evaluation:")
print(f"  Predictions: {all_rumor_preds}")
print(f"  True labels: {all_rumor_labels}")
print(f"  Prediction counts: {dict(Counter(all_rumor_preds))}")
print(f"  True label counts: {dict(Counter(all_rumor_labels))}")
print(f"  Computed accuracy: {rumor_acc}")
```

**问题**：
- 每个 epoch 都打印完整预测列表
- 如果验证集有 1000 个样本，就会打印 1000 个预测值
- 拖慢终端输出和日志 I/O

---

### 问题 5：缓存机制没有真正接入训练流程

**代码位置**：
- `src/data/llm_explanation_generator.py` 第 202-213 行：有 `cache_explanations()` 和 `load_cached_explanations()` 方法
- `src/data/dataset.py` 第 117-144 行：`_generate_explanations()` 方法

**问题**：
- 虽然有缓存方法，但 `dataset.py` 的训练流程里**没有调用**
- 每个 epoch 都会重新生成 explanation
- 唯一的"缓存"是依赖数据 JSON 里预存的 `explanation` 字段

**影响**：
- 如果数据里没有预存 explanation，训练时会重复调用 API
- 训练不可复现（每次生成的 explanation 可能不同）
- 浪费大量时间和 API 费用

## 🔍 如何判断训练是否正常

### 正常的训练应该：
- ✅ 每个 epoch 在几分钟到十几分钟内完成（取决于数据集大小）
- ✅ GPU 利用率明显波动（20%-80%）
- ✅ 显存占用稳定（几 GB 到十几 GB）
- ✅ 训练 loss 逐渐下降
- ✅ 验证 accuracy 逐渐上升

### 异常的训练表现：
- ❌ 每个 batch 都卡很久（几十秒到几分钟）
- ❌ GPU 利用率很低（< 10%）
- ❌ 日志里出现大量 API 错误或超时
- ❌ 训练 loss 不下降或剧烈波动
- ❌ 验证 accuracy 长期低于 0.5（二分类）

## 📞 常见问题

### Q: 为什么原代码这么慢？
**A:** 因为 `use_mock_llm: false`，每个样本都调用 DeepSeek API，有 1 秒延迟。

### Q: 为什么准确率只有 0.33？
**A:** 多重原因：训练轮数太少、LLM 生成不稳定、配置过重。修复后应该会改善。

### Q: 可以直接改回 200+100 epoch 吗？
**A:** 不建议。先用 10+5 验证，再逐步增加。

### Q: 可以改回真实 LLM 吗？
**A:** 不建议直接训练时用。应该先离线生成 explanation，写回数据，再训练。

### Q: 这个模型到底是二分类还是四分类？
**A:** 都有。主任务是谣言二分类，辅助任务是立场四分类。训练日志里的 `rumor_acc` 是二分类准确率。

---

**总结：原代码的核心问题是训练时在线调用 LLM，导致极慢且不稳定。修复后应该能在几小时内完成 15 个 epoch 的验证训练。**
