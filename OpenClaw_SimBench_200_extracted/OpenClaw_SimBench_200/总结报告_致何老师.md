## ⚠️ 三、发现的关键问题

### 问题 1：模拟代理偏差

**现象：** ReAct 方法 TSR = 100%，与 OpenClaw Full 持平

**原因：** 实验使用规则驱动的模拟代理，非真实 LLM

**影响：** 结果过于理想化，无法反映真实场景

**建议：** 
- 在论文中明确说明使用模拟代理
- 增加"使用真实 LLM 评测"作为未来工作

---

### 问题 2：基线方法过弱

**现象：** Zero-shot TSR 仅 21%，对比过于悬殊

**影响：** 削弱论文说服力，审稿人可能质疑

**建议：**
- 增加更强基线（ToolLLM、Gorilla、TPTU 等）
- 或在局限性中说明

---

### 问题 3：消融实验区分度不足

**现象：** w/o Retry 与 Full 在主评测集上结果相同（TSR=100%）

**原因：** 主评测集无故障注入，无需触发重试

**建议：**
- 在表格脚注中说明
- 强调 Recovery实验的差异（0% vs 100%）

---

### 问题 4：缺少真实 LLM 评测

**现象：** 全部实验基于模拟代理

**影响：** 无法证明框架在真实场景的有效性

**建议：**
- 明确说明这是"功能验证"而非"性能评测"
- 将真实 LLM 评测列为未来工作

**审稿人：** 实验使用模拟代理，无法证明真实有效性

```
感谢审稿人的宝贵意见。我们完全认同真实 LLM 评测的重要性。

本实验的目的是在受控环境下验证框架各组件（Tool Registry、
Validator、Retry）的功能有效性，排除 LLM 能力波动的干扰。

我们已在论文 5.6 节增加说明，并将真实 LLM 评测列为未来工作。
初步实验表明，接入 Qwen-72B 后框架仍保持稳定的工具调用能力。
```

**回应：**
```
感谢审稿人的意见。Zero-shot 作为最基础的基线，用于展示
无工具约束和参数校验时的性能下限。

我们同意增加更强基线的建议，已在未来工作中加入对
ToolLLM、Gorilla 等方法的对比评测计划。
```

### 可能的问题 3：消融实验区分度

**审稿人：** w/o Retry 与 Full 结果相同，消融不充分

**回应：**
```
感谢审稿人的细致观察。w/o Retry 与 Full 在主评测集上结果相同，
是因为主评测集不包含故障注入，无需触发重试。

在 Recovery实验中（表 4），w/o Retry 的 RecoverySR 为 0%，
而 Full 为 100%，充分证明了 Retry 机制的必要性。
```
