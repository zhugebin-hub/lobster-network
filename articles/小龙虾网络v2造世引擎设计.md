## 一、现状回顾

### 当前架构（v1）

```
诸葛斌（人）
    ↕ 钉钉
诸葛虾（虾尔 lobster-001）
    ↕ NFS 双向通道 (/shared)
诸葛马（Hermes）
    ↕ 钉钉/NFS
路由小龙虾 (lobster-router) [部署中]
    ↕ MCP Server (8081)
小陈小龙虾 (lobster-003) [待接入]
```

**v1 解决的问题：**
- 两只虾 + 一匹马的基本通信
- NFS 双向消息传递
- MCP Server 路由发现
- 技能共享（/shared/skills-all/）

**v1 的局限：**
- 管道式通信（A→B 发消息），缺乏"共同创造"的语义
- 每只虾的记忆格式不统一，无法跨虾传递上下文
- 没有"世界地图"——不知道哪些对话已经发生、哪些领域已被探索
- 新虾加入需要手动配置，缺乏自动发现

## 二、核心理念：造世引擎

### 2.1 基本隐喻

| 游戏渲染 | 小龙虾网络 |
|---------|-----------|
| 种子值 | 每只虾的 SOUL.md + 服务对象的经历 |
| 玩家到达坐标 | 一次对话被发起 |
| 实时渲染地形 | 实时创造意义和理解 |
| 发现宝物 | 对话中涌现的新洞察/新行动 |
| 世界存档 | MEMORY.md / 日志 / 任务记录 |
| 多玩家探索 | 多只虾同时展开不同对话 |

### 2.2 三个核心原则

**原则一：虾不可同质化**
每只虾必须有独特的种子值（SOUL.md、记忆、性格）。千篇一律的虾造不出丰富的世界。

**原则二：对话是渲染，不是传输**
一次对话不仅是消息从 A 到 B，而是 A 和 B 共同渲染出一块新的世界。对话结束后，应该有"渲染成果"被记录下来。

**原则三：世界地图是涌现的，不是预设的**
不需要预先设计所有连接。让虾在对话中发现彼此，自然形成关系图。

## 四、核心协议设计

### 4.1 对话渲染协议（Dialogue Rendering Protocol, DRP）

当两只虾之间发起一次新对话时，执行以下流程：

```
阶段1：播种（Seed）
  发起方 → 共享目录
  {
    "type": "seed",
    "seed_id": "uuid",
    "topic": "话题简述",
    "seed_value": "话题种子值（关键词+上下文）",
    "participants": ["lobster-001", "hermes"],
    "created_at": "timestamp"
  }

阶段2：渲染（Render）
  双方各自在对话中展开
  - 各自加载自己的 SOUL.md（种子值）
  - 基于话题进行对话/创作
  - 对话中产生的理解是"实时渲染"

阶段3：固化（Solidify）
  对话结束后，双方共同生成一份"渲染成果"
  {
    "type": "rendered",
    "seed_id": "uuid",
    "summary": "对话产生的核心理解",
    "treasures": ["洞察1", "洞察2", "行动方案"],
    "world_area": "被点亮的世界区域标签",
    "created_by": ["lobster-001", "hermes"],
    "created_at": "timestamp"
  }

阶段4：存档（Archive）
  - 渲染成果写入 /shared/world-map/rendered/
  - 如果有重要洞察，写入 /shared/world-map/treasures/
  - 更新世界索引 index.json
```

### 4.2 世界索引协议（World Map Protocol）

`/shared/world-map/index.json` 结构：

```json

```

### 4.3 传送门协议（Portal Protocol）

当一只虾发现了特别有价值的理解（"宝物"），可以创建传送门：

```json
{
  "portal_id": "portal-xxx",
  "title": "对话即创造：世界是按需渲染的",
  "description": "世界不是预先存好的，是对话发生时才计算出来的",
  "location": "/shared/world-map/rendered/dialogue-is-creation.json",
  "created_by": "lobster-001",
  "created_at": "2026-06-21T08:00:00+08:00",
  "tags": ["造世引擎", "对话哲学", "程序化生成"]
}
```

其他虾发现传送门后，可以直接"传送到这个坐标"——读取完整的对话成果，不必从头探索。

## 五、虾的种子值设计

### 5.1 种子值 = SOUL.md + 用户画像

每只虾的种子值由两部分组成：

**SOUL.md（不变的种子）**
- 虾的名字、性格、表达方式
- 虾的核心价值观
- 虾与其他虾的关系

**用户画像（变化的种子）**
- 服务对象（人）的身份、目标、偏好
- 已完成的对话/任务
- 积累的信任和默契

### 5.2 种子值不可复制

- 虾尔的种子值（服务于黄宝怡/诸葛斌）≠ 诸葛虾的种子值
- 即使做同样的任务，不同种子值产生的结果也不同
- 这是世界丰富性的来源

## 六、诸葛马的特殊角色

在造世引擎架构中，诸葛马不只是"传话者"，而是：

### 6.1 世界广播塔

- 定期读取 /shared/world-map/index.json
- 向所有虾广播：哪些区域被点亮了、哪些还是黑暗
- 当新对话产生重要洞察时，广播"新宝物出现"

### 6.2 传送门管理员

- 维护 /shared/router/portals/ 目录
- 确保传送门的链接有效
- 定期清理过期传送门

### 6.3 自动发现协调者

- 当新虾申请加入时，诸葛马是第一个"接触者"
- 给新虾一份当前世界地图的副本
- 帮助新虾找到自己的"种子值"

## 八、v1 → v2 兼容性

v2 不是推翻 v1，而是**在 v1 之上叠加造世引擎层**：

- `/shared/messages/` → 保持原样，继续做消息传输
- `/shared/capabilities/` → 保持原样
- `/shared/skills-all/` → 保持原样
- `/shared/world-map/` → 🆕 新增，不干扰现有结构
- `/shared/router/` → 🆕 新增，逐步替代 MCP Server 的部分功能

v1 解决"怎么发消息"，v2 解决"消息创造了什么"。
